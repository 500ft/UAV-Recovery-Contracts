3. WORKING RULES FOR THE ENTIRE WEEK
======================================================================

Evidence and reproducibility

- Pin every external identity by immutable version or commit. A documentation
  URL is not a firmware pin.
- Store raw simulator outputs and derived normalized traces separately.
- Every run directory must contain a manifest that points to the exact command,
  commit, configuration hash, seed, event class, and input files.
- Hash source files used to extract the model. If source bytes change, the model
  validation identity changes.
- Never overwrite a prior evidence directory. Use a new dated directory.
- Keep invalid runs. Mark them invalid with a reason; do not delete them or
  silently remove them from denominators.
- Never turn an empty result into a success, and never turn a simulator crash
  into a safety observation.

Scientific boundaries

- SITL results are simulation evidence. They do not establish hardware timing,
  flight safety, fleet safety, or safe operation outside the registered domain.
- A verified null is a result: if no unsafe composition is reachable under the
  frozen model and scope, report it rather than adding hazards until something
  is found.
- A model disagreement is evidence about model fidelity. It is not allowed to
  be hidden by changing the model structure after validation runs.
- The model may be repaired only for a pre-registered guard-input modelling
  error. A change to discrete state structure requires a new model identity,
  new validation seeds, and a new validation record.
- Do not compare PX4 with ArduPilot this week. Do not make brand-level claims.
- Do not use “safe,” “validated,” “guaranteed,” “proven,” or “real-world” for
  this work. Use “matches the registered SITL criterion” when appropriate.

Ponytail / scope discipline

- Reuse the repository's manifest schema, tests, provenance patterns, and event
  vocabulary wherever possible.
- Do not build a new model checker. Use UPPAAL/verifyta only if it is actually
  available and its version is recorded. If it is unavailable, produce the
  model contract and a blocker; do not replace it with an unreviewed homemade
  reachability engine.
- Do not add a general plugin architecture, database, web dashboard, or fleet
  allocator. They are unrelated to the first trace.
- One vehicle, one pinned PX4 release, one simulator model, six single-event
  classes, two parameter configurations per class, and fixed seeds are enough
  for the first validation matrix.

Task T2.2 — Define the event state machine

Files: protocols/authority-loss-trace.schema.json; docs/specs/formal-
composition/study-a-protocol.md; docs/specs/formal-composition/
decisions-2026-09-19.md

Define these event states and allowed transitions:

PRECONDITIONING -> NORMAL_TRACKING -> EVENT_SCHEDULED -> INPUT_INTERRUPTED
-> MONITOR_TRIGGERED -> ACTION_SELECTED -> MODE_OBSERVED -> TERMINAL_OR_TIMEOUT
-> RECONNECT_ATTEMPTED -> AUTHORITY_ACCEPTED_OR_REJECTED.

The trace must record which transition was observed and which was not. Do not
infer a transition from elapsed time alone.

For each event, specify:

- the exact interrupted signal or process;
- publisher identity and message type;
- the final accepted setpoint/heartbeat timestamp;
- the scheduled and observed interruption timestamps;
- monitor name and configured delay;
- first action/mode selected and every later mode change;
- commands or setpoints that continued to exist from other publishers;
- reconnect stimulus, acceptance/rejection, and authority owner after return;
- terminal mode, disarm state, or timeout reason;
- clock source, units, sampling rates, and alignment rule.

The normalized trace must retain raw mode names, raw action names, and a list of
unmapped values. Normalization may add labels; it may not erase ambiguity.

Done when a valid fixture and at least three invalid fixtures are specified:
missing final setpoint, non-monotonic clock, and mode transition before event
injection. Invalid traces are rejected with stable error codes.

Task W3.1 — Specify the runner contract

Files: tools/sitl/README.md; tools/sitl/run_px4_case.py; tests/
test_sitl_runner_contract.py

The runner interface should be one command shaped like:

    python tools/sitl/run_px4_case.py \
      --matrix protocols/px4-study-a-matrix.json \
      --case PX4-OFFBOARD-LOSS-NOMINAL-1001 \
      --out evidence/task-formal-composition-2026-09-19/runs/

The exact CLI may change, but it must provide the same contract:

1. Resolve one case from the frozen matrix.
2. Refuse missing or mismatched firmware/configuration/source hashes.
3. Create an isolated run directory before launching the simulator.
4. Write the resolved manifest before injection.
5. Launch the pinned PX4 SITL process with explicit working directory and
   environment.
6. Verify NORMAL_TRACKING before injecting the event.
7. Inject exactly one registered event at the scheduled time.
8. Capture raw stdout/stderr, telemetry, mode/action events, and exit status.
9. Stop at terminal state or registered horizon.
10. Validate and normalize the trace.
11. Return nonzero for setup, capture, or schema failure; return zero for a
    completed valid run even if the observed behavior differs from the model.

The runner must not silently download software, choose a default configuration,
retry an event with a different seed, or overwrite an existing run directory.

Done when the contract test can exercise argument parsing, missing-case refusal,
output-directory refusal, and valid-run/invalid-run exit behavior without
starting PX4.

Task W3.3 — Verify lockstep reproducibility

Files: evidence/task-formal-composition-2026-09-19/README.md; run manifests;
tests/test_sitl_runner_contract.py

- event and transition timestamps;

Task R4.3 — Freeze the four Study B properties

Files: protocols/unsafe-composition-properties.json; models/px4-study-a/
properties.q; docs/specs/formal-composition/study-a-protocol.md

Encode these properties exactly as the merged protocol defines them:

U1. A hazard remains active beyond its configured delay plus 1.0 second without
    an engaged failsafe action.

U2. Two hazards are active and the engaged action has lower documented priority
    than the highest active hazard's action.

U3. An action engages and disengages without the hazard clearing, more than once
    in ten seconds.

U4. Time from hazard onset to a terminal safe mode exceeds the sum of configured
    delays plus 2.0 seconds.

For every property record:

- formal query;
- natural-language interpretation;
- units and clock semantics;
- required model state;
- expected witness format;
- whether a violation can be replayed in SITL;
- known false-positive/false-negative limitations;
- status: planned, not executed.

Do not call the terminal modes safe in a universal sense. Use “registered
terminal mode” in implementation prose and reserve “unsafe composed state” for
the operational definition in the protocol.

Done when an independent reviewer can determine what a witness means without
opening the model source.

Task F5.2 — Write the validation and disagreement decision tree

Files: docs/specs/formal-composition/study-a-protocol.md; evidence/task-formal-
composition-2026-09-19/README.md

Use this exact decision tree:

1. Setup or recording failure -> invalid run; preserve it; do not count it.
2. Valid run, model sequence matches, timing within registered thresholds ->
   agreement.
3. Valid run, sequence differs -> root-cause as simulator artifact, injection
   artifact, guard-input modelling error, or model-structure error.
4. Guard-input modelling error -> repair only the guard abstraction, create a
   new model hash, and rerun the registered validation set.
5. Model-structure error -> stop; do not patch after the fact. Reopen the model
   design and restart validation with a new identity.
6. Agreement >=95%, median timing error <=0.2 s, p95 <=1.0 s -> proceed to Study B.
7. Agreement 90–95% -> proceed only with every disagreement root-caused and
   documented, and obtain owner approval before checker interpretation.
8. Agreement <90% -> kill the formalization on this model and release the
   conformance/trace benchmark as the valid floor.
9. Study B reaches no U1–U4 witness -> report a verified null; do not add new
   hazards to create a positive result.
10. Study B produces witnesses -> replay every witness in SITL. Report confirmed,
    refuted, and invalid witnesses separately.
11. Any confirmed interaction -> prepare an upstream issue draft, but do not
    submit it without owner approval and a separate disclosure review.

Done when this tree is cited by the run report, model README, and final claim
ledger update.

7. FORMAL-MODEL DESIGN DETAILS CLAUDE MUST NOT SKIP
======================================================================

Source-to-model traceability

For each automaton transition, include a table with:

- model component and transition;
- PX4 source path and symbol;
- parameter names used;
- guard condition;
- timer/reset behavior;
- expected observable trace channel;
- abstraction status: exact, interval, or assumed;
- validation test that can expose an error.

This table is more important than a large model file. If a transition cannot be
traced to code or protocol, it is a hypothesis and must be labeled as such.

Priority and interaction semantics

The model must specify what happens when two hazards are active at once. Record
the source-backed priority order, exception flags, and whether a later event can
preempt an active action. Do not derive priority from the order in which code
was read or from an observed trace alone.

Clock semantics

Use one declared time unit in the model and trace. Record how simulator time,
message timestamps, wall-clock timestamps, and injected-event timestamps relate.
Never compare wall time to simulated time without a declared conversion.

Continuous guard abstraction

The initial model may use interval-valued battery, estimator, geofence, or
position inputs. For each interval, record lower/upper bound, source of the
bound, assumed rate, and whether the abstraction is conservative for the
property. If monotonicity is not demonstrated, flag the property as potentially
inconclusive and trigger the hybrid-reachability decision from scope.md.

Reconnection and user takeover

Study A may log reconnection and takeover even if the first formal model does
not include them as state. Explicitly label those channels as observed-but-out-
of-model. Do not claim the model covers reconnection until it has an automaton,
property, and validation test.

Immediate application to the SITL/model-validation work

1. Define the expected outcome before accepting the produced artifact.
   For a small single-event fixture, derive the expected action and timing
   bounds from the pinned parameter values, source semantics and an explicit
   hand-worked event timeline. Keep this calculation separate from the model
   translator and trace normalizer. The docs simulator shares PX4 code: it is
   useful for extraction consistency, but is not an independent validation
   of the underlying control logic or physical behavior.

2. Separate successful execution from verified behavior.
   A process exit, checker completion, command acknowledgment, screenshot or
   populated log is insufficient. Accept a run only when its required files
   parse, hashes and case identity agree, and the required event observations
   exist. If the comparison oracle or a required observation is missing,
   record verification as unverified; never infer a pass from execution status.
   This is a requirement for the later implementation, not a new status schema
   introduced by this planning supplement.

3. Prove that the input change reached the system.
   Log requested injection, observed input cessation, surviving publishers,
   monitor activation, selected action and observed mode separately. A line
   written by the injector saying "fault sent" is not independent observation
   that the fault occurred. Confirm whether the pinned transport actually
   permits separate liveness and setpoint interruption before treating those
   as distinct executable cases.

4. Add a controlled parameter-change check during harness development.
   Read back one relevant failsafe parameter, change it within its supported
   range, and repeat the same development case. Predict the affected timing
   or action from the pinned code before running it. Verify both effective
   parameter readback and the expected behavioral change; account for clamps,
   exceptions and other active timers. Restore and verify the baseline value.
   This catches a parameter file that was written but never applied. These
   development runs do not count as held-out model-validation cases.

5. Probe coordinates and clocks before interpreting traces.
   Use known input values to verify axis signs, frame transforms, units and
   time alignment. Check the raw and normalized values numerically. Do not
   infer orientation from a plot, API name or remembered convention. Freeze
   tolerances justified by the channel resolution and logging rate; CAD's
   reported floating-point agreement is not a UAV timing tolerance.

6. Validate trace export and re-import.
   For a tiny known fixture, save the normalized trace, reload it through the
   consumer, and compare case identity, units, timestamps, event ordering,
   mode labels, row count and invalid-run flags with the declared conversion
   contract. Explicitly account for any intentional resampling. Retain the
   original raw log so a plausible derived file cannot conceal missing data.

7. Instrument each stage and test silent failure.
   Retain stage-level results for launch, configuration application, normal
   tracking, injection, capture, normalization and comparison. Include focused
   negative fixtures for unapplied parameters, ineffective injection and a
   stale result from another case. Associate asynchronous outputs with the
   launched job/case and its hashes; a returning launch call does not establish
   completion. Bound waits and preserve timed-out attempts as such.

8. Preserve the acquisition route of every physical input.
   Distinguish designer-selected provisional dimensions, vendor-drawing values
   and physical measurements if later hardware enters the project. A drawing
   does not satisfy a requirement for a physical measurement. Amend the route
   explicitly before relying on a different kind of evidence. Missing required
   values stay unresolved; they do not receive plausible invented numbers.

Apply items 1-7 to the existing trace-contract, runner, reproducibility and
model-review tasks. They are acceptance checks within those tasks, not a
separate CAD workstream or an expansion into physical testing.
